# Grill with Docs for Codex

让当前 Codex 主代理负责访谈、代码与文档核查、方案写入和用户沟通；让 subagent 只读审查。全程不依赖外部编程代理或嵌套 Codex CLI。

本 skill 是 `grill-me-codex` 的文档感知替代入口，不与其同时运行。若另一规划流程已拥有任务，继续该流程，除非用户明确要求切换到本工作流。本 skill 不主动发现、调用或假设存在任何第三方 skill。

需要建立或更新领域文档时，使用本 skill 附带的 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 和 [ADR-FORMAT.md](./ADR-FORMAT.md)。只在实际需要写入时读取对应模板。

## 读取项目语言

开始前检查：

- 根目录 `CONTEXT-MAP.md`；
- 相关上下文中的 `CONTEXT.md`；
- 根级和上下文级 `docs/adr/`；
- 相关代码、测试、`AGENTS.md` 和现有方案。

若 `CONTEXT-MAP.md` 存在，按映射定位相关上下文。若没有上下文文档，不预先创建空文件；在第一个术语真正达成共识时再创建。

## 逐项访谈并同步文档

一次只问一个会影响方案的问题，并给出推荐答案。优先从代码库查证可查事实。特别检查：

- 用户用词是否与现有 `CONTEXT.md` 冲突；
- 模糊术语是否混用了不同领域概念；
- 用户描述是否与当前代码行为矛盾；
- 边界条件和具体场景是否会推翻当前理解；
- 是否存在明显更简单的方案。

术语确认后由主代理立即更新对应 `CONTEXT.md`。它只记录领域词汇、边界和关系，不写实现步骤。

仅当决定同时满足以下条件时，向用户建议 ADR：难以逆转、没有背景会令人困惑、确实经过方案权衡。用户确认后再由主代理写入 ADR；不要为普通实现细节创建 ADR。

## 冻结方案

决策树解决、术语同步完成后，将方案写入 `PLAN.md`，使用项目的规范术语，并包含：目标、成功标准、步骤、关键决策、受影响路径、验证、风险与回滚、范围外事项。创建 `PLAN-REVIEW-LOG.md`，记录文档变化和默认最多三轮审查。

## 多视角审查

根据风险并行启动最多三个只读 subagent：

1. **领域一致性**：核对方案、`CONTEXT.md`、ADR 和代码中的术语及边界。
2. **正确性与架构**：检查状态、数据、安全、并发、迁移和失败模式。
3. **验证与运行**：检查测试、验收、回滚、可观测性和部署顺序。

只给每个 reviewer 必需的文件路径、角色和输出契约，不传递预期结论。要求每个问题包含严重度、证据、影响和最小修复，并以 `APPROVE` 或 `REVISE` 结尾。reviewer 不得修改任何文件。

主代理合并、核实并裁决结果，只由主代理更新方案、上下文文档、ADR 和日志。复审时继续使用相同 reviewer，并提供修订方案和上一轮处置；最多三轮。不能收敛时公开剩余分歧交给用户。

若当前 surface 没有 subagent 能力，主代理按三个角色进行顺序复查并说明降级，不调用外部编程工具。

## 最终确认

展示最终方案、术语/ADR 变化、审查改进和残余风险。用户明确确认前不实现产品代码。用户随后要求实施时，结束本规划流程，让新的请求根据方案声明和已安装 skill 的描述自动选择执行流程；不要要求用户手动输入另一个 skill 名称。

## 硬性规则

- `CONTEXT.md` 是领域词汇表，不是实现规范。
- ADR 必须稀少且有真实权衡。
- 主代理是唯一文档与方案写入者；reviewer subagent 始终只读。
- 不硬编码模型，不把 subagent 描述成跨模型审查。
- 一次只问一个问题，审查最多三轮，未解决分歧交给用户。
