# Codex Build

在当前 Codex 会话内完成实现和验证。不要启动嵌套 Codex CLI，不要绕过沙箱或审批，不要让多个 agent 同时写同一工作树。主代理始终拥有范围判断、最终审查、用户沟通和提交权限。

先确定执行流程所有权。若方案头部、用户指令或当前活动流程已经指定其他执行器，退出本 skill 并遵循该流程；同一方案只能有一个执行主流程。本 skill 不主动发现、调用或假设存在任何第三方 skill，只负责自身定义的实施、审查和验证流程。

## 实施前门槛

默认读取 `PLAN.md`；接受用户指定的其他方案路径。开始前确认：

1. 方案已获用户批准，目标、边界和成功标准明确。
2. 已读取相关代码、测试、`AGENTS.md` 和项目验证命令。
3. 已运行 `git status --short` 并记录基线。保留用户现有改动，不覆盖、不回滚、不把无关文件纳入结果。
4. 验证命令可从方案或项目中确定；若无法安全确定，只问用户一个必要问题。

若脏工作树中的改动与计划路径重叠，暂停并说明冲突。若改动不重叠，可在清楚记录基线后继续。不要要求用户为了流程形式提交或 stash 无关改动。

若方案仍要求新的产品决策，停止实现并把任务退回规划或计划审查状态，让后续请求根据描述重新路由。若任务非常小且做一次直接修改更简单，主代理直接完成，不增加 delegation 开销。

## 保持单一写入者

默认由主代理实现。只有在方案完整、任务边界清晰且 delegation 明显有益时，才可启动一个 builder subagent；启动前明确其允许修改的路径、禁止触碰的范围和必须运行的验证。builder 工作期间不得有其他写入型 agent。

无论由谁写入，都必须：

- 严格按冻结方案实施，不重新设计；
- 只修改直接相关文件；
- 先建立失败用例或复现路径，再修复 Bug；
- 不提交、不推送、不发布；
- 报告偏离方案之处及原因。

## 主代理验证

写入完成后，主代理必须亲自：

1. 重新读取 `git status` 和相对基线的完整 diff。
2. 检查方案符合度、项目风格、范围和用户原有改动是否完整保留。
3. 运行聚焦测试，再按风险运行更广验证。
4. 将实际结果与方案成功标准逐项对应。

builder 的报告和测试输出只是线索，不能代替主代理的 diff 审查和验证。

## 独立只读审查

所有写入停止后，根据风险启动一至两个只读 reviewer subagent：

- **实现审查**：检查方案符合度、正确性、安全、回归和越界修改。
- **验证审查**：检查测试是否真正覆盖成功标准、失败路径和操作风险。

给 reviewer 方案路径、基线说明、完整 diff 范围和验证结果；不要给预期答案。要求其不修改文件，并返回严重度、证据、影响、最小修复以及 `APPROVE`/`REVISE`。

主代理核实发现后亲自修复，或在仍使用同一 builder 且边界明确时发送一次精确 follow-up。每次修复后重新运行验证，并让 reviewer 只复查未解决问题。默认最多两轮；达到上限仍有实质问题时停止并向用户说明，不能用反复 delegation 掩盖失败。

没有 subagent 能力时，主代理进行独立的第二遍 diff 与测试审查，并明确说明降级路径。

## 交付与提交门槛

向用户报告：实现摘要、变更文件、验证命令与结果、审查轮次、方案偏差和残余风险。只有用户明确同意后才能提交；推送、发布和其他外部变更需要各自授权。

## 硬性规则

- 同一时间只有一个写入者。
- 主代理必须读取完整 diff 并亲自运行验证。
- reviewer subagent 始终只读，不能提交或修复。
- 不使用嵌套 Codex CLI，不绕过沙箱或审批，不硬编码模型。
- 用户批准方案不等于批准提交、推送或发布。
