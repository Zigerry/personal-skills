# Codex Plan Review

让当前 Codex 主代理负责上下文、用户沟通和最终判断；让 subagent 提供独立、只读、职责分离的审查。不要启动嵌套 Codex CLI，不要假设 subagent 使用不同模型，也不要在审查阶段修改产品代码。

## 设置边界

默认使用：

- `PLAN_FILE=PLAN.md`
- `LOG_FILE=PLAN-REVIEW-LOG.md`
- `MAX_ROUNDS=3`

接受用户明确提供的替代值，并在开始前简短说明。若任务明显简单、低风险且一个直接检查即可完成，指出更简单的做法，不为形式而启动多代理流程。

读取方案、相关代码、`AGENTS.md` 和项目验证命令。若方案不存在或仍包含会改变整体方向的关键歧义，先让用户补充，或把任务退回需求澄清状态，让后续请求根据描述重新路由；不要在审查中默默替用户决定。

本 skill 可以审查任何来源的方案，但只负责计划级审查，不替代代码 diff 审查。若另一规划流程仍在产出方案，等待其完成后再审查，不并行争夺方案所有权，也不主动调用产生该方案的其他 skill。

## 建立独立审查

根据风险选择一至三个审查角色：

1. **需求与范围**：检查歧义、遗漏、相互矛盾、隐含假设和更简单方案。
2. **正确性与架构**：检查数据流、状态、并发、安全、迁移、兼容性和失败模式；只关注与任务相关的维度。
3. **验证与运行**：检查测试、验收标准、回滚、可观测性、部署顺序和操作风险。

优先并行启动独立 subagent。给每个 reviewer 最少且完整的任务上下文：方案路径、相关代码范围、审查角色和输出格式。不要传递主代理的预期答案或其他 reviewer 的结论。明确要求：

- 只读分析，不修改任何文件，不提交代码，不联系用户。
- 每个问题包含严重度、方案章节或代码证据、影响和最小修复建议。
- 没有实质问题时明确写 `APPROVE`；存在阻塞问题时写 `REVISE`。
- 区分确认事实、合理推断和需要用户决策的问题。

如果当前 Codex surface 没有 subagent 能力，由主代理按相同角色进行彼此分离的顺序审查，并明确说明这是降级路径。不要改用外部编程工具或嵌套 Codex CLI。

## 汇总并收敛

主代理逐条核对 reviewer 结论，合并重复项，拒绝缺乏证据或超出范围的建议，并记录理由。只让主代理修改 `PLAN_FILE` 和 `LOG_FILE`。

每轮在日志中记录：

- reviewer 的实质发现；
- 已接受的修改；
- 被拒绝的建议及理由；
- 尚需用户决定的分歧；
- 本轮结论 `APPROVE` 或 `REVISE`。

修订后优先让相同 reviewer 复查，向其提供新方案和上一轮处置结果，要求只验证未解决项和新增风险。达到 `MAX_ROUNDS` 仍未收敛时停止循环，列出剩余分歧交给用户，不伪造批准。

## 最终确认

向用户展示最终方案、关键改进、审查轮次和仍存在的风险。获得明确确认前不开始实现。用户之后明确要求实施时，结束计划审查阶段，让新的实施请求根据已安装 skill 的描述和方案声明自动选择执行流程；不要要求用户手动输入另一个 skill 名称。

## 硬性规则

- 主代理拥有最终判断，subagent 只提供建议。
- 审查 subagent 始终只读；同一时间不得有写入型 agent 修改工作树。
- 不硬编码模型，不把独立上下文描述成跨模型验证。
- 不允许无限循环；默认最多三轮。
- 方案批准和代码提交是两个独立的人类确认点。
