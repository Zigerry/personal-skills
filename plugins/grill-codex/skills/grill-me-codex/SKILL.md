# Grill Me for Codex

全程留在当前 Codex 工作流中。主代理负责访谈、代码库探索、方案写入和用户沟通；subagent 只负责独立审查。不要调用外部编程代理或嵌套 Codex CLI，不要在方案获批前编写产品代码。

若另一规划流程已经拥有当前任务，继续该流程，不叠加第二套访谈、方案文件或确认门槛。只有本 skill 被用户明确请求或由描述匹配选中时，才由它负责从访谈到方案审查；它不主动发现、调用或假设存在任何第三方 skill。

## 第一阶段：逐项明确方案

先复述目标和已知约束。若代码库能够回答问题，先检查真实文件、配置、测试和历史约定，不把可查事实抛给用户。

沿决策树一次只问一个问题，并等待回答后再继续。每个问题：

- 说明它影响的具体决策；
- 给出主代理推荐答案和简短理由；
- 存在多种合理解释时明确列出，不默默选择；
- 发现更简单的方案、代码矛盾或逻辑不一致时立即指出；
- 不询问不会改变方案或验收标准的偏好。

持续维护已确认决定、开放问题、范围外事项和成功标准。只有当所有会改变实现方向的分支都已解决，才结束访谈。

## 冻结方案

将共识写入 `PLAN.md`：

```markdown
# Plan: <task>

## Goal
## Success criteria
## Approach
## Key decisions and tradeoffs
## Files and boundaries
## Verification
## Risks and rollback
## Out of scope
```

验收标准必须可执行；Bug 修复包含复现用例，新校验包含异常输入测试，重构包含原有测试。创建 `PLAN-REVIEW-LOG.md`，记录方案由用户与 Codex 共同确认，审查轮数默认上限为三轮。

## 第二阶段：独立审查

根据风险并行启动最多三个只读 subagent，分别审查：

1. 需求、范围、歧义和更简单方案；
2. 正确性、架构、安全和失败模式；
3. 测试、验收、回滚和运行风险。

给 reviewer 最少且完整的上下文，只提供方案路径、相关代码范围、角色和输出契约。要求其不修改文件，并为每个发现给出严重度、证据、影响和最小修复；结尾写 `APPROVE` 或 `REVISE`。

主代理核对并合并结果，只接受有证据且与目标相关的建议。修订 `PLAN.md`，把接受、拒绝和未决项写入日志。需要复审时优先继续使用相同 reviewer，最多三轮；达到上限仍有分歧则交给用户决定。

没有 subagent 能力时，主代理按三个角色顺序独立复查，并向用户说明降级；不要转向其他编程工具或嵌套 CLI。

## 最终确认

展示最终方案、审查带来的关键改进、轮数和残余风险，并询问用户是否批准方案、是否进入实施。只有明确确认后才能写产品代码。用户随后要求实施时，结束本规划流程，让新的请求根据方案声明和已安装 skill 的描述自动选择执行流程；不要要求用户手动输入另一个 skill 名称。

## 硬性规则

- 一次只问一个有决策价值的问题。
- 主代理是唯一方案写入者和最终裁决者。
- reviewer subagent 始终只读，不接触用户，不提交代码。
- 不硬编码或切换模型；subagent 代表独立上下文，不代表不同模型。
- 审查有限轮次，未收敛时公开分歧，不伪造批准。
